# セキュリティ設計

本製品は「個人情報を扱うための道具」であるため、
**道具自身が漏洩経路になってはならない**という原則で設計しています。

---

## 1. 守るべき資産

| 資産 | 説明 | 漏洩した場合の影響 |
|---|---|---|
| **原文（個人情報）** | マスク前の文字列 | 最重大。本製品の存在意義が失われる |
| **Vault（対応表）** | プレースホルダ ⇄ 原文 | 同上。復元表があれば全原文が復元できる |
| **API キー** | 上流 LLM の認証情報 | 課金・不正利用 |
| **設定** | 転送先 URL 等 | 中 |

---

## 2. 脅威モデル

想定する攻撃者と、それぞれへの対策です。

| # | 脅威 | 対策 | 実装 |
|---|---|---|---|
| T1 | **上流 AI に原文が渡る** | 送信前にマスク | `proxy.mask_payload` |
| T2 | **悪意ある Web サイトがローカル API を読む** | Origin 制限 + 403 | `proxy._local_origin_guard` |
| T3 | **Vault ファイルを覗かれる** | AES-GCM で暗号化、鍵は 0600 | `vault._encrypt_bytes` |
| T4 | **会話 A の復元表が会話 B に適用される** | セッション分離 | `vault.SessionVaults` |
| T5 | **ローカルネットワークから API を叩かれる** | 既定で `127.0.0.1` にのみ bind | `config.host` |
| T6 | **API キーがログ・応答・設定に残る** | 応答から除外、既定で非保存 | `config.to_public_dict` |
| T7 | **マスク漏れ** | 多層検出 + 検出プレビュー + 統計 | `detect.py` |
| T8 | **復元漏れ（プレースホルダが残る）** | 3 段構えの復元 + `restore_misses` 計上 | `masking.unmask` |

---

## 3. 実装上の対策詳細

### 3.1 ネットワーク露出

既定では `127.0.0.1` のみに bind します。`0.0.0.0` にすると
同一ネットワークの他端末から管理 API を叩けてしまうため、
明示的に変更しない限り外部から到達できません。

```python
host: str = "127.0.0.1"   # 既定
```

> **警告:** `--host 0.0.0.0` を指定すると、管理 API
> （`/admin/api/mapping` は原文を返します）が LAN に露出します。
> 必要な場合はファイアウォールかリバースプロキシで保護してください。

### 3.2 オリジン制御

```python
_ALLOWED_ORIGIN_RE = re.compile(
    r"^(?:https?://(?:localhost|127\.0\.0\.1|\[::1\])(?::\d+)?"
    r"|(?:tauri|https?)://tauri\.localhost"
    r"|tauri://localhost)$"
)
```

`Origin` ヘッダを持つ要求は、ローカル系オリジン以外すべて **403** で拒否します。
`Origin` を送らない CLI / SDK / curl はそのまま通ります。

これは特に `/admin/api/mapping`（原文を返す）と
`/admin/api/state`（設定を変更できる）を守るために重要です。

### 3.3 Vault の暗号化

```
nonce = os.urandom(12)
ciphertext = AESGCM(key).encrypt(nonce, plaintext, aad=b"jp-pii-mask-v1")
保存形式 = nonce(12B) || ciphertext
```

- 鍵は 32 バイトの乱数。`~/.jp-pii-mask/key.bin` に `0600` で保存
- AAD によりコンテキストを束縛（他の用途への流用を防止）
- 鍵が無い場合は生成。`cryptography` が無い場合は平文にフォールバック
  （その場合でもファイル権限は 0600 に設定）

**テストで検証済み:** 保存ファイルのバイト列に原文が含まれないこと
（`test_masking.py::TestVaultPersistence::test_saved_file_is_not_plaintext`）。

### 3.4 API キーの扱い

| 経路 | 既定の挙動 |
|---|---|
| 環境変数 | 読み取る。ディスクに残らない |
| 制御パネル / GUI から入力 | `store_api_key=false` ならディスクに残さない |
| 保存する場合 | 設定ファイルを 0600 に設定 |
| 管理 API の応答 | **常に空文字を返す**（`api_key_set` の真偽のみ） |

`GET /admin/api/state` がキーを返さないことはテストで検証しています。

### 3.5 ログ

- マスク件数・種別のみを記録し、**原文は記録しません**
- `access_log` は既定で無効
- 統計は `requests_total` / `entities_masked` / `placeholders_restored` /
  `by_type` など、原文を含まない数値のみ

## 4. 既知の制限とリスク

### 4.1 マスク漏れ（最も重要なリスク）

**本製品は「検出漏れゼロ」を保証しません。**

- 未知の姓、難読名、ひらがなのみの人名は取りこぼす可能性があります
- 文脈に依存しない略称・愛称・社内用語は検出できません
- 画像・PDF・`multipart/form-data` はマスクせず素通しします

**緩和策:**
1. 制御パネルの「検出テスト」で、送信前に実際の文面を確認する
2. `custom_terms` に社内固有の固有名詞を登録する
3. 重要な用途では `redact_only` モード（復元しない完全消去）を使う
4. 統計の `entities_masked` が 0 のまま送信していないか確認する

### 4.2 復元漏れ

モデルがプレースホルダを大きく書き換えた場合、復元できません。
`restore_misses` で検知できます。値が増えている場合は
プロンプトを見直すか、プレースホルダ形式の説明をシステムプロンプトに含めてください。

### 4.3 同一端末の他ユーザー

Vault の鍵は OS のファイル権限に依存します。
同一ユーザーとして動く別プロセスからは読めます。
端末自体が共有される環境では、OS のユーザー分離に依存してください。

### 4.4 メモリ上の中間状態

マスク中は原文とプレースホルダが同時にメモリ上に存在します。
スワップアウトした場合、ディスクに残る可能性があります
（OS レベルの対策であり、本製品では制御しません）。

### 4.5 上流 API の信頼

本製品は「送信前に伏せる」だけで、上流 API の扱いを変えるものではありません。
転送先の選定は利用者の責任です。

## 5. セキュリティチェックリスト（導入時）

- [ ] `--host` を変更していない（既定の `127.0.0.1` のまま）
- [ ] `store_api_key` は必要時のみ `true`
- [ ] `~/.jp-pii-mask/` の権限が適切（鍵が `0600`）
- [ ] `custom_terms` に自組織固有の固有名詞を登録
- [ ] 制御パネルの「検出テスト」で自組織の典型的な文書を確認
- [ ] `restore_misses` が増えていないか定期的に確認
- [ ] ログを外部に転送する場合、原文が含まれないことを確認

---

## 6. 脆弱性の報告

セキュリティ上の問題を見つけた場合は、公開イシューではなく
非公開の経路で報告してください。

**最も重大なのは「マスク漏れ」です。**
再現手順と、どの種別が漏れたかを添えて報告いただけると助かります。
